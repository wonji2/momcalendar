### 0-2. 우리가 정한 방법 (추천이 아니라 결정 · 근거는 0-1)
1. **배포: Workers 정적 자산(Workers Paid $5/월, Wrangler 4.34.0 이상 고정)**, 저장소 `wonji2/momcalendar` 는 그대로 비공개 전환. `html_handling = "none"`(`.html` 주소가 307 로 바뀌지 않게). 그러면 확장자 없는 주소(라이브에서 `/terms /privacy /admin /register /staff /approve` 가 200 인 것 확인)와 `/폴더/` 주소가 404 가 되므로 **Worker 가 대신 처리**한다: 자산에 없는 경로만 Worker 로 오고, ① `/terms` → `/terms.html` 을 **주소 변경 없이 200** 으로 서빙 ② `/폴더/` → `/폴더/index.html` ③ 오래 마감된 gg 는 R2 에서 ④ 그래도 없으면 `404.html` 을 **404 상태**로. (`not_found_handling` 은 Worker 가 못 받게 막을 수 있어 설정하지 않는다.)
2. **파일 수 방어**: 사이트 파일은 지금 약 57,100개이고 **하루 약 750개씩 늘어 약 57일 뒤 10만을 넘는다.** 그래서 **장기 마감 gg 페이지(build.ps1 의 C 계층: 사이트맵 제외·noindex·200 유지)는 R2 에 HTML 로 두고**, 자산에 없는 주소만 Worker 가 R2 에서 꺼내 준다. 산식: gg 37,550 − (A/B 계층 ≈ 사이트맵 상한 11,500 + 보존 명단) ≈ 2.5만이 R2 대상 → 자산 ≈ 3.2~3.4만(정확한 개수는 1단계 시험 배포에서 build.ps1 판정 결과로 확정). 빌드가 **자산 예산 5만 개를 지키도록 가장 오래된 C 계층부터 R2 로 보내는 순환**을 하고, 게이트는 6만에서 경보·8만에서 배포 중단(70% 경보만으로는 못 막는다는 Codex 지적). R2 서빙은 키 규칙(경로 → 객체 키, 한글 퍼센트 인코딩·대소문자 구분)·`Content-Type`·`Cache-Control`·404 를 명세하고 2단계 시험 목록에 R2 쪽 URL 을 합쳐 넣는다. R2 비용은 객체 약 2.5만 · 약 230MB(무료 10GB·A급 100만 이내), 요청은 엣지 캐시로 B급 1,000만 이내.
3. **도메인: 존이 이미 Cloudflare(네임서버 gabriel/melissa.ns.cloudflare.com)라 DNS 위임이 필요 없고, apex 인증서는 이미 발급돼 있다**(2026-11-25 실측: `curl --resolve momcalendar.com:443:<Cloudflare IP>` 가 TLS 검증 통과 후 200. GitHub 쪽 인증서는 2026-12-27 만료). 순서는 6절. **「무중단」이라고 단정하지 않고 「컷오버 새벽에 최대 수 분의 불안정 + 1~5분 안에 되돌리기」로 설계한다**(프록시 레코드 TTL 은 자동 300초). 리허설 호스트 `stg.momcalendar.com` 에서 Custom Domain·Route 두 방식과 롤백을 시험하되, apex 의 실제 레코드·HSTS·존 규칙은 그대로 재현되지 않으므로 apex 전용 사전 점검(존 설정 대조, 위 인증서 실측)을 따로 한다.
4. **예약 작업: 시계(clock) 24시간 연쇄 실행은 폐기하고 이미 운영 중인 Supabase pg_cron `public.gh_dispatch('<워크플로>.yml')`(origin 의 `supabase/sql/red_autofix_kick_150.sql` · `seo_kick_190.sql` 에 정의·사용 중, 세분화 토큰은 Vault `github_dispatch_token` · 저장소 한정 Actions 읽기/쓰기)로 각 작업을 제시간에 `workflow_dispatch`** 한다. (오늘 만든 로컬 미배포 `gh-dispatch` Edge 함수·`gh_schedule_cron_145.sql` 은 이 안으로 **대체되어 쓰지 않는다**.) 시계와 겹쳐 이중 실행되지 않게 **작업 하나씩 pg_cron 으로 옮기며 그 작업만 시계의 `CLOCK_ONLY` 목록에서 뺀다**(27개 항목 · 마지막에 시계 `schedule` 제거). 시계의 「이미 실행 중이면 건너뛰기·20분 뒤 재확인」은 `concurrency` 그룹과 워크플로의 「오늘 이미 돌았으면 건너뜀」으로 대신하고, pg_cron 자체 장애는 기존 `gh-clock-watch` 와 같은 심박 감시로 잡는다. 근거: schedule 지연은 공식 한계, 외부에서 dispatch 는 공식 방법, 24시간 연쇄는 약관 소지와 분 낭비(시계 1,440분/일). 시계가 만든 「정시·누락 없음」 효과는 그대로 얻는다.
5. **Actions 분: 비공개 전환의 선행 조건 = 호스티드 분을 월 3,000분 안으로.** 핫딜 수집·손님 화면 검사(합 3,330분/일)는 서버(Edge+pg_cron) 또는 전용 Linux 러너로 옮긴다(self-hosted 는 문서상 분 차감 없음). 요금 개편 여부는 결제 직전 재확인.
6. **비밀값: 교체가 먼저, 기록 재작성은 하지 않는다**(공식: 교체하면 재작성은 필요 없을 수 있고, 재작성은 포크·캐시에 못 미친다). 옛 기록에 남은 값 중 **현재도 살아 있는 것만** 새로 만들어 교체(7절 순서). 비공개 전환은 새 노출을 막으려는 용도.
7. **옛 기록 지우기·새 저장소 이전은 하지 않는다**(별도 지시가 있을 때만). 이유: 효과 한계 + 해시 변경으로 여러 세션이 같은 폴더를 쓰는 지금 사고 위험.

## 6. 컷오버 순서 (단계마다 되돌리기)
**0단계(사장님 결제·토큰 뒤)**: 라이브 기준표 생성(파일 목록·sha256·상태·헤더). 존 설정 대조표(SSL 모드·Always HTTPS·Browser Cache TTL·Rocket Loader·이메일 난독화·AI 크롤러/봇 차단·ECH) 기록.
**1단계 시험 배포(손님 영향 0)**: `wrangler.jsonc` → `*.workers.dev` 로만 배포. 되돌리기 = Worker 삭제.
**2단계 동등성 시험(합격이 컷오버 조건)**: 사이트맵 약 2.8만 URL + 나머지 무작위 5,000 + 루트 파일 전부 + `.well-known/assetlinks.json`·`tdmrep.json`·`404.html`·`robots.txt`·`sitemap*.xml` 이름으로 + 한글·띄어쓰기·대소문자만 다른 `g/NON-GMO.html` vs `g/Non-gmo.html`·`g/VOOKS.html` vs `g/Vooks.html`: 라이브와 비교해 상태 200 동일 · **리다이렉트 0** · 바이트 해시 · Content-Type · `Cache-Control` 일치. 존재하지 않는 주소는 404 동일. 확장자 없는 `/terms`·`/privacy`·`/admin` 등이 라이브에서 200 인지 먼저 확인하고(GitHub 는 서빙) 필요하면 별도 처리. 실제 브라우저 4길(live_smoke) · 서비스워커 · 푸시 등록 호출(save-push-sub CORS). 하나라도 불일치면 컷오버 중단.
**3단계 파이프라인 교체(라이브는 아직 GitHub)**: 새 워크플로가 같은 게이트를 통과한 판을 Cloudflare 에도 올린다(이중 배포). 한쪽 실패 = 전체 실패, 직렬화 그룹 유지. 업로드 뒤 확인은 URL 3개가 아니라 표본 200개. `backup/last-good` 은 Cloudflare 업로드와 표본 통과 뒤에 갱신, `wrangler rollback` 보조.
**4단계 리허설 호스트 `stg.momcalendar.com`**: Custom Domain 과 Route 를 둘 다 붙여 보고 **공백(오류 응답)이 없는 방식**을 채택, 롤백(10초 주장)을 실제로 잰다. GitHub 인증서 만료일 > 컷오버+14일 확인.
**5단계 컷오버(새벽 02~05시, 사장님 시각 승인)**: SSL 모드 Full(strict) · Always HTTPS 확인 → apex 에 채택한 방식 적용(Route 라면 Route 먼저 → 프록시 전환) → 5분 점검(서버 헤더·표본 200개·로그인·찜·핫딜·푸시 등록) → 이상 시 즉시 되돌리기. 목록 호출 주소(select 칸)는 이 작업과 함께 바꾸지 않는다(DB 정지 사고 교훈). 컷오버 뒤 GitHub Pages 는 **7일 유지**.
**6단계 7일 관찰**: 손님 화면 검사·구글 색인(일일 표본)·오류 레이더 = 컷오버 전과 동일. Search Console 크롤 오류 매일.
**7단계 비공개 전환**: §4 분 조건 충족 + §5 수정 배포 완료 뒤. 전에 apex A 레코드 정리(도메인 가로채기 방지). 되돌리기 = 다시 공개(별·구독은 복구 불가, 포크는 분리 영구).
**R2 보관 단계**(0-2의 2): 오래 마감된 gg 페이지 → R2, 자산에 없는 주소만 Worker 가 R2 에서 응답. 2단계 시험에 포함.
